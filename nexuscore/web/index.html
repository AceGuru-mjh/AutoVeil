/ Four-Layer Architecture

四层分离详解

底层稳定与上层灵活的严格隔离。每层有且仅有一个职责，跨层通信只通过定义良好的接口。

LAYER 01

Root 守护核心层

NexusDaemon · C++17 / Rust
系统的绝对控制中枢。随 init 启动，不被系统杀死。
  • Watchdog 线程级重启 + PID 文件
  • SELinuxManager 仅修补自身域
  • FileSystemInterceptor OverlayFS / Bind 降级
  • IpcServer UDS + SO_PEERCRED
  • RootEnvDetect Magisk/KSU/APatch 适配
LAYER 02

抽象与调度层

Abstraction & Orchestration
连接 Daemon 与 UI 的桥梁。MVP 解析清单、执行脚本，预留事件总线。
  • IModuleLoader priority 排序挂载
  • ShellExecutor 独立 Mount NS 执行
  • IProcessIsolator CLONE_NEWNS 隔离
  • IEventBus in-memory Pub/Sub
  • 所有接口为纯虚类 / Trait
LAYER 03

客户端与管理层

NexusManager · Kotlin / Compose
用户交互、IPC 通信、状态可视化。绝不直接执行 Root 命令。
  • NexusIpcClient 断线重连 + 连接池
  • Dashboard / Modules / Logs 三页
  • MVVM + StateFlow
  • 所有 IPC 走 Dispatchers.IO
  • ZIP 安装通过 FileBridge 桥接
LAYER 04

模块与插件生态

Module Ecosystem · DMM
声明式模块清单替代 module.prop，为 Agent 化预留插槽。
  • manifest.json 元数据 + 能力 + 意图
  • capabilities 最小权限白名单
  • intents 事件订阅声明
  • priority 冲突排序字段
  • 未声明能力一律 CAPABILITY_DENIED
/ Developer Guide

开发指南速览

三步构建你的第一个 NexusCore 模块。完整规范见 spec-03 与 SDK 文档。

my_module/manifest.json
// 声明式模块清单 (DMM)
{
  "id": "my_module",
  "name": "My First Module",
  "version": "0.1.0",
  "author": "you",
  "min_nexus_version": "1.0",
  "priority": 0,
  "capabilities": [
    "EXECUTE_SHELL",
    "MOUNT_FILESYSTEM"
  ],
  "intents": [
    { "action": "SYSTEM_BOOT_COMPLETED" }
  ]
}
01
创建模块骨架 mkdir -p my_module/system
02
编写 manifest.json + 脚本 声明 capabilities，未声明的能力会被拒绝
03
打包为 ZIP zip -r9 ../my_module.zip .
04
Manager 安装 + 重启 从本地 ZIP 安装 → 重启生效
05
验证与调试 adb shell cat /data/adb/nexuscore/logs/<id>.log
/ Evolution Roadmap

从 MVP 到超纲生态

"MVP 验证核心 → 架构预留插槽 → 逐步注入超纲功能" 的渐进策略。每个 Phase 有明确触发条件，避免过度工程。

PHASE 1

MVP · 四层架构闭环

Daemon + Manager + 示例模块（NexusProp Editor）。OverlayFS/Bind 挂载、SELinux 内存修补、SO_PEERCRED IPC、声明式清单。

● 已完成 · 工程落地成功率 90%+
PHASE 2

FUSE 幻影文件系统

触发条件：OverlayFS 在 Android 15/16 出现严重性能瓶颈或兼容性问题时

实现 IFileSystemInterceptor 的 FUSE 版本。基于 libfuse 用户态文件系统，结合正则/AST 解析实现"千 App 千面"动态文件生成。MVP 已预留 prepareFuse() 接口插槽。

○ 下一阶段 · 接口已预留
PHASE 3

意图总线与内存缝合

触发条件：模块数量增加，出现 build.prop 或系统文件覆盖冲突时

重构 IModuleLoader，引入 Pub/Sub 事件总线。模块对系统属性的修改从"物理覆盖"转变为"内存中的意图缝合"，多模块同路径叠加而非覆盖。

○ 架构预留 · EventBus 抽象已就位
PHASE 4

Agent 运行时与状态机

触发条件：基础功能稳定，开始追求"自适应"和"智能化"时

Daemon 内嵌轻量脚本引擎（Lua / Wasm）。模块可声明 REGISTER_AGENT 能力，基于状态机根据系统温度、内存状态自动调整行为，实现"自演化模块"。现有 .sh 脚本无需重写。

○ 架构预留 · capabilities 已含 REGISTER_AGENT
PHASE 5

App 隔离沙盒（需求已收缩）

需求收缩：原"整机无重启平行宇宙"受 Zygote 全局 NS 限制无法完美实现，改为 App 级隔离沙盒

深度整合 Linux Namespace（PID/Mount/Network/UTS），针对单个 App 实现独立模块配置集热切换。不挑战 Zygote 全局命名空间，规避崩溃与变砖风险。

⚠ 需求已收缩 · 风险显著降低
/ Optimization Points

已落地整改与小优化点

严重问题已在 MVP spec 中当场解决（不记录为"待办"）。以下为已落地的关键整改与持续优化方向。

跨机型 OverlayFS 兜底 整改#1
内核不支持 OverlayFS 时自动切换 Bind Mount；均不可用进入只读模式。EROFS 上目标不存在则跳过并告警，不阻断启动。
spec-01 §6.2-6.5 · FsDetector::select()
Root 环境依赖校验 整改#2
Daemon 启动期检测 Magisk/KSU/APatch，自动适配 sepolicy 路径与 overlay 存储目录。Unknown provider 进入只读模式，避免误操作变砖。
spec-01 §5.1 · RootEnvironmentDetector
IPC 凭证校验 整改#3
SO_PEERCRED 校验客户端 UID + SELinux 域 + 包名 + APK 签名指纹四重校验。陌生 APP 连接立即被关闭，防止越权调用 Root 能力。
spec-01 §10.2 · CredentialCheck
Phase 5 需求收缩 整改#4
"整机无重启切换系统"改为"App 隔离沙盒"。规避 Zygote 全局命名空间硬限制，大幅降低崩溃、变砖风险。
spec-01 §1.3 · Web 路线图 Phase 5
模块冲突机制 整改#5
IModuleLoader 按 DMM priority 字段升序挂载，高优先级覆盖低优先级。Phase 3 事件总线完成内存缝合，多模块同路径叠加。
spec-01 §7.3 · spec-03 §6
Bootloop 防护
连续 2 次未到 boot_completed 自动进入安全模式；失败计数器 ≥3 强制 safe_mode 文件存在。所有 syscall 失败均有 fallback，绝不 _exit(1) 触发 init 重启风暴。
spec-01 §13
日志双写 + 滚动
内存 ring buffer 供 IPC 实时订阅 + 落盘 512KiB 滚动 ×3。绝不写 stderr，避免 init 早期重定向丢失。
spec-01 §4.2
脚本超时与隔离
所有 .sh 在独立 Mount Namespace 执行，120s 超时 kill。退出码 2 标记模块 disabled，下次启动不加载。
spec-01 §7.4 · spec-03 §7.2
Manager 断线自愈
指数退避 + 抖动重连，所有 pending 请求断线立即失败避免挂起。SharedFlow 多订阅者共享事件流。
spec-02 §3.3-3.4
能力最小权限
capabilities 白名单强制校验。未声明 EXECUTE_SHELL 却提供 service.sh → 跳过并记录 CAPABILITY_DENIED。
spec-03 §3.2 · §4
签名指纹防伪
Manager APK 签名 SHA256 白名单。伪造 Manager 即使同包名同 UID 也会被 Daemon 拒绝。
spec-01 §10.2 · CredentialCheck::authorize
URI → tmp 桥接
SAF URI 无法被 root Daemon 直接读，FileBridge 复制到 /data/local/tmp 再传路径。避免权限边界穿透。
spec-02 §6.5
